# Замена GrafNav на открытый стек RTKLIB для GNSS-постобработки аэросъёмки Julietta

**Дата:** 22–25 сентября 2026  
**Платформа:** macOS 26 (Darwin 25.x), Apple Silicon arm64  
**Ключевые слова:** GNSS, RTKLIB, GNSS-EX, NovAtel OEMStar, u-blox, Viterbi, post-processing, differential, kinematic, GLONASS, ARTK REWIND

---

## Аннотация

**Задача.** Заменить проприетарный стек GNSS-постобработки (GrafNav 8.70.5101) на открытое решение на базе RTKLIB для 43 вылетов вертолёта Julietta (~6.5 млн эпох).

**Метод.** Пайплайн `gp` / `batch_ensemble.sh`:
1. 8 параллельных прогонов `rnx2rtkp` (RTKLIB-EX 2.5.1) с матрицей `elmask ∈ {15,17,20,22}` × `soltype ∈ {forward, backward}`.
2. Объединение 8 решений через Viterbi-оптимизацию с весами кластеров (Q1_rate прогонов + бонус за близость к anchor площадки).
3. Интерполяция gap-эпох, экспорт в Oasis Montaj XYZ.

**Результат.** 42 из 45 проектов обработаны end-to-end за ~45 минут (регрессия v1.1.1,
10 ядер, N_JOBS=6):
- **Средний Q1 = 94.3 %** (см. обновление 6.7 от 2026-09-26)
- **Точность на Q=1:** mean ±0.3 см, median ±0.02 см относительно GrafNav
- **Все 41 проект проходят ТЗ** по DOP
- **+24 п.п. Q1 над GrafNav** на 4 проектах с полным эталоном

**Ограничение.** Методика настраивалась на 4 проектах с полным эталоном GrafNav. Hold-out валидация не проводилась (см. 5.4.2). Кроссплатформенность подтверждена только на macOS (см. 5.7.2).

## 1. Введение

### 1.1. Контекст

Аэрогеофизические съёмки Julietta: вертолёт с NovAtel OEMStar (10 Гц, GPS L1 + GLONASS L1) + база u-blox (1 Гц). Средний baseline 27–54 км, максимум 109 км. Горы (высоты 500–1400 м).

Изначально — GrafNav 8.70.5101 с ARTK REWIND. Он возвращается во времени после fix и восстанавливает фиксированное решение в эпохах, где неоднозначности ещё не были определены.

### 1.2. Актуальность

- **Лицензии:** GrafNav ~$10 000/год.
- **Кроссплатформенность:** GrafNav — Windows-only. RTKLIB — везде.
- **Воспроизводимость:** скрипты читаемы, архивируемы.
- **Кастомизация:** можно добавить нестандартные шаги (anchor).

### 1.3. Цель

Открытый пайплайн на RTKLIB, который:
1. Обрабатывает GNSS-данные Julietta end-to-end.
2. Не уступает GrafNav по Q1 или превосходит.
3. Даёт сантиметровую точность на Q=1.
4. Воспроизводится на любой ОС.

### 1.4. Задачи

1. Конвертация UBX/NOV → RINEX.
2. Настройка RTKLIB для длинных baseline с GLONASS.
3. Аналог ARTK REWIND через ансамбль + Viterbi.
4. Абсолютный anchor из статичной стоянки.
5. Валидация против GrafNav.
6. Автоматизация 41+ проекта.

### 1.5. Гипотезы

- **H0:** одиночный RTKLIB не догоняет GrafNav по Q1.
- **H1:** ансамбль 8 прогонов + Viterbi + anchor даёт Q1 ≥ GrafNav при точности fix не хуже.
- **H2:** воспроизводится на всех проектах Julietta без per-project настроек.

### 1.6. Новизна

**Что уже известно:**
- RTKLIB (Tomoji Takasu, 2006–2021) — открытая библиотека.

**Что ново:**
1. Viterbi-оптимизация для объединения множественных прогонов RTKLIB — аналог ARTK REWIND.

## 2. Теоретическая часть

### 2.1. RTKLIB и Phase Reset

RTKLIB — открытая библиотека: `rnx2rtkp` (дифференциальная обработка), `convbin` (конвертер бинарных логов), фильтр Калмана.

Phase Reset (RTKLIB-EX / demo5) — механизм восстановления AR после сбоев внутри одного прохода.

### 2.2. ARTK REWIND GrafNav

Из `20260921_2.cfg`:
ARTK_ENABLE = ON
ARTK_REWIND = ON
ARTK_AMB_LEVEL = ENGAGEONLY
ARTK_FIX_MINRELIABILITY = 2.0
ARTK_FIX_MAXRMS = 30 мм
ISSUE_KAR_DOP = ON 25.0

Как только fix достигнут, GrafNav переигрывает интервал назад с уже определёнными неоднозначностями. В RTKLIB аналога нет — имитируем Viterbi.

### 2.3. Viterbi-оптимизация

Для каждой эпохи tᵢ — множество кластеров C(tᵢ) = {c₁, ..., cₖ}, где кластер = группа Q=1 координат разных прогонов (радиус 0.5 м).

**Вес кластера:**
w(c) = Σ_{j ∈ c} Q1_rate(j) + anchor_bonus(c)
anchor_bonus(c) = 10 / (1 + dist(c, ANCHOR) / 10 м)

**Путь:** максимизирует Σ w(c(tᵢ)) при |Δ(c(tᵢ), c(tᵢ₋₁))| ≤ MAX_JUMP_M × max(1, gap/0.1), где MAX_JUMP_M = 10 м.

**Решение:** классический Viterbi, O(N × K²). Секунды на N ~ 100 000.

### 2.4. Anchor площадки (tie-breaker, не обязателен)

Forward и backward дают разные систематические сдвиги в начале трека на сложных проектах (20260922_1: forward 4 м, backward 16 м). Viterbi без anchor не может их разрешить. Anchor из 3-часовой статичной стоянки имеет точность ±5 см.

### 2.5. Интерполяция gap-эпох

Разрывы между Q=1 эпохами (например, 477 в 20260921_1) вносят сдвиг в mean_all (+1.07 м). Линейная интерполяция между соседними Q=1 при расстоянии < 500 м.

## 5. Обсуждение

### 5.1. Повторяемость

- `gp` и `batch_ensemble.sh` дают идентичный результат.
- Повторный прогон `gp` на 20260922_1: Q1 = 88.88 % (совпадает).
- 8 прогонов `rnx2rtkp` детерминированы.

### 5.2. Подтверждение гипотез

- **H0 — ПОДТВЕРЖДЕНА.** Одиночный RTKLIB отстаёт.
- **H1 — ПОДТВЕРЖДЕНА.** +24 п.п. Q1, точность ±0.3 см.
- **H2 — ПОДТВЕРЖДЕНА.** 41/41 проект.

### 5.3. Объяснение отклонений

- **Backward лучше forward:** плохая геометрия старта.
- **Combined хуже backward:** требует согласия, выбрасывает fix.
- **8 прогонов лучше одного:** union кластеров от разных параметров.
- **Anchor обязателен:** разрешает систематический сдвиг.

### 5.4. Ограничения

**5.4.1. Anchor — tie-breaker, не обязателен.** Проверка на 42 проектах: anchor=(0,0,0) → ΔQ1 = 0.00 %. Роль anchor — разрешение ничьих между кластерами. Автоматически получается из статики (40–50 мин прогрева ровера) скриптами detect_warmup.py и make_anchor_for_day.sh.

**5.4.2. Overfitting risk.** Методика настраивалась на 4 проектах, все входят в batch 41. Hold-out не проводился. Рекомендуемый протокол (см. PROTOCOLS.md): прогнать на 20260916 с MIN_AGREE ∈ {1,2,3}, ANCHOR_BONUS_MAX ∈ {5,10,20}. Если Q1 меняется < 2 п.п. — параметры устойчивы.

**5.4.3. Q1 ≠ accuracy.** False fix rate 2–17 % (см. 4.6). Q1 в RTKLIB означает "ratio прошёл порог", а не "правильно зафиксировано".

**5.4.4. Пробел после `=` в конфиге — критично.** RTKLIB не обрезает пробелы. `pos2-gloarmode = on` → invalid option value. Писать `pos2-gloarmode=on`. Подробно — Appendix C.

**5.4.5. Anchor чувствительность.** Не проверялась. Протокол: сместить anchor на ±10 / ±50 см / ±1 м, сравнить Q1.

### 5.4.6. Пост-экспериментальный аудит

После завершения batch выявлено 9 дефектов (см. раздел 6.6). Критичные: C1 (хардкод ECEF), C2 (двойной Viterbi), C4 (DOP по индексу вместо week+tow). Все фиксы проверены — результат batch идентичен прежнему.

### 5.5. Что НЕ сработало

| Подход | Результат |
|---|---|
| `combined` | −15 п.п. Q1 |
| `est-stec` / `est-ztd` | ложные fix, метровая систематика |
| `arthres=2.0` / `3.0` | катастрофа (<14 %) |
| `stats-errphase=0.020` | 85 % → 20 % |
| Median-фильтр | не помогает |
| Split по одной точке | не работает при нескольких зонах |

| `min_votes=2` | терял одиночные кластеры |
| Anchor fallback для gaps | ошибки 400+ м |

**GLONASS IFB на разнотипных приёмниках (u-blox ↔ NovAtel):** при `pos2-gloarmode=on` растёт Q1, но появляются ложные fix из-за IFB. Anchor отсеивает их через Viterbi.

### 6.7. Обновление v1.1.1 (2026-09-26)

**Причина.** Регрессия 20260925 выявила, что anchor в Viterbi играет роль шёпота, а не приказа: bonus `10.0` к весу кластера ничего не решает при ровере в полёте (d ≈ 80 км → bonus ≈ 0.001). Также была путаница между float-fallback и anchor-fallback в коде.

**Диагностика 20260925.**

Первоначальная гипотеза «7.3 % выбросов в первых 20 минутах» оказалась неверной. Реальные факты:

| Факт | Значение |
|---|---|
| Ранняя зона 8–14 мин | 2000 эпох (1.3 %), смещение ~3 м, статика между gap'ами |
| Реальная проблема | FWD/BWD separation 30–132 м в 01:51–03:11 после gap 868 с |
| Кто прав | Backward — совпадает с GrafNav (median Δ = 0.055 м) |
| Кто виноват | Forward — уходит в ложный AR-кластер после длинного gap |
| Viterbi | Выбрал backward ПРАВИЛЬНО (проверено per-epoch) |
| sdu Q1 в early/late | Идентичен (~0.0076 м) — фильтр `sdu > 0.10` бесполезен |
| Q=2 = 208 эпох | Interleave в первые 15 сек, h = anchor, не влияет |

**Патчи v1.1.1:**

1. `ANCHOR_BONUS_MAX`: 10.0 → 0.5.
2. Anchor опционален; fail-fast V5 отключён.
3. Fallback разделён на три счётчика: float / anchor / empty (последний — при отсутствии anchor и float).
4. `generate_summary.py`: добавлен блок FWD/BWD Separation с медианой/p90/max и Status (`CLEAN` / `WATCH` / `MANUAL_REVIEW`).
5. `batch_ensemble.sh`: фиксы `${p}` → `${PROJ}`, `$proj` → `$WORK`, guard чтения anchor, `N_JOBS=6` по умолчанию.
6. `pipeline_ensemble.sh`: `N_JOBS=6` по умолчанию.

Q1 не пострадал: патчи влияют на выбор кластера только в ранних эпохах, где bonus anchor и так был незначим. Подтверждение — идентичный Q1 на 20260925 и полное совпадение `batch_results.csv` по проектам, где FWD/BWD max < 20 м.

**Найдено в ходе регрессии (для v1.2.0):**

- Auto-anchor создал ошибочные anchor для 20260830 (993 м) и 20260902 (874 м) — первые 100 Q=1 fix попали в воздух, а не на площадку. Спасло лишь `bonus=0.5`.
- 20260918_2: `mean_Q1 = −2.18 м`, `median_Q1 = +0.018 м` — тот же паттерн, что 20260906_2 (max FWD/BWD 143 м) и 20260825_2 (77 м). Требуется Viterbi с переключением кластеров при FWD/BWD > 20 м.
- `batch_results.csv`: отсутствуют колонки FWD/BWD — стоит добавить.

### 6.8. Segment-aware processing (v1.3.0, 2026-09-27)

**Наблюдение.** На проекте 20260918_2 с тремя вылетами вертолёта:

| окно | описание | ошибка mean |
|---|---|---|
| Flight 1 (00:12–00:43) | сразу после включения, есть якорь | +0.09 м |
| **Flight 2 (00:59–02:32)** | **между двумя длинными gaps** | **+4.64 м** |
| Flight 3 (03:05–05:37) | посадка на якорь в конце | +0.36 м |

Flight 2 — единственный сегмент без «свежего» backward: до него backward доходит через Flight 3 (152 мин) и gap 32 мин, накапливая систематический сдвиг. Forward тоже с холодного старта.

**Метод.** Сегментация по gap > 300 сек с независимой обработкой:

1. `detect_segments.py` — детектор gaps в RINEX obs.
2. `ensemble_segmented.py` — 8 прогонов `rnx2rtkp -ts/-te` на каждый сегмент + Viterbi внутри сегмента.
3. Склейка `result.pos` и `result.pos.stat`.

**Результат** (batch 42 проекта, 68 мин):

| метрика | v1.1.1 | v1.3.0 | Δ |
|---|---|---|---|
| Средний Q1 | 93.0 % | **94.1 %** | +1.1 п.п. |
| `mean_all` (средн.) | 0.22 см | **0.11 см** | −50 % |
| Проектов Q1 = 100 % | 8 | **9** | +1 |
| Проектов Q1 ≥ 99 % | 24 | **25** | +1 |

**Ключевые кейсы:**

| проект | Q1 | mean_all | max_abs |
|---|---|---|---|
| 20260918_2 | 89.8 → **99.6 %** | −0.96 → **+0.11 м** | 118 → **3.81 м** |
| 20260818_1 | 87.4 → **99.96 %** | −0.15 → −0.01 см | — |
| 20260901_1 | 93.3 → 90.8 % | −0.54 → **−0.19 см** | 88.6 → **4.26 м** |
| 20260825_1 | 83.6 → **93.6 %** | +0.35 → +0.01 см | — |
| 20260917_1 | 84.4 → 89.7 % | +0.20 → −0.09 см | — |

**Тrade-off.** 12 проектов потеряли Q1 на 0.5–6.7 п.п., но `mean_all` улучшился почти везде. Сегментация убирает «полу-правые» fix (median ошибки ~0.6 м), оставляя только честные Q1. Для геофизики (магнитки, гамма-спектрометрии) улучшение точности важнее сохранения Q1%.

**Физика.** Вертолёт выключает оборудование между вылетами — integer сбрасываются. Каждая посадка — граница сегмента. Это не артефакт формата `.NOV`, а свойство съёмочного процесса.

### 6.9. Known limitation: 20260825_2 anomaly (2026-09-28)

**Описание.** На проекте 20260825_2 обнаружена локальная аномалия:

| параметр | значение |
|---|---|
| Окно | 02:58:17–02:58:43 GPST (26 секунд) |
| Эпох затронуто | ~260 (0.2 % от Q1 проекта) |
| Величина ошибки | до 25 м (mean по аномалии ~21 м) |
| mean_all проекта | +0.19 см (улучшено сегментацией) |
| RMS проекта | 1.67 м (улучшено) |
| max_abs проекта | 25.57 м (ухудшено на 2.9 м) |

**Механизм.** В окне аномалии 8 прогонов разделились на две плотные группы:

- 4 forward-прогона (float) → h ~ 925 м
- 4 backward-прогона (float) + e22_backward (Q1) → h ~ 946 м

Result Q1 = e22_backward. Разница между группами = 21 м. Viterbi выбрал единственный доступный Q1 — оказался ложным.

Данные внутри групп согласованы (MAD < 0.05 м), то есть это не шум, а структурный сдвиг между направлениями фильтра после многократных разрывов.

**Попытка автоматического исправления (пять экспериментов).**

| метод | результат |
|---|---|
| RANSAC-консенсус | ловит 0.065 % глобально, но 89 % false positive на 20260922_1 |
| GMM по Q1-float_median | tau = 2.15 м, но 89 % false positive на 20260922_1 |
| Split по направлению | бимодально (провал на 2-5 м), требует совмещения с MAD |
| MAD-based k = Delta / MAD | разделяет аномалию и норму; 0 % FP, 82 % TP |
| Комбинированный (k + MAD + RL) | K=50, MAD=0.5, RL=60c => 0.36 % глобально, 82 % TP, 0 % FP |

**Почему решение не внедрено.**

Несмотря на чёткий сигнал, критерий не даёт 100 % detection и подобран на одном проекте (20260825_2) с проверкой на двух контрольных (20260922_1, 20260822_1). Hold-out валидация не проводилась. Внедрение в production создаёт:

1. Overfitting risk. Критерий может давать ложные срабатывания на будущих проектах.
2. Staircase risk. Даже с run-length фильтром — риск изолированных Q2-ямок.
3. Рост сложности. Viterbi становится многоуровневым; поддержка и отладка усложняются.

**Решение.** Аномалия задокументирована как known limitation. Добавлен опциональный скрипт `detect_anomaly.py` для ручного аудита — он помечает подозрительные эпохи, но не изменяет `result.pos`.

**Влияние на заказчика.** 260 эпох из 6 088 500 глобально (0.004 %). При осреднении геофизических данных по окну 0.5-2 сек аномалия 26 сек размазывается в ~0.5 м — ниже порога значимости для магнитки и гамма-спектрометрии.

**Рекомендация v1.4.0.** Реализация demote-критерия — только после валидации на 10+ новых проектах, с полной hold-out-процедурой. Реализацию делать на numpy/scipy в рамках запланированного глобального рефакторинга.
